1. What the Cron Does

Command: auto:deliverynoteverification
File: app/Console/Commands/AutoDeliveryNoteVerify.php
Schedule: Configurable via global_settings (type = delivery_note_auto_verification_time). If that setting is missing, the cron is never scheduled.

Purpose: Every day at the configured time, find all unverified delivery notes that riders have submitted, re-stamp the latest shipment journey status for each shipment, trigger payment generation for delivered shipments, escalate stuck Reason-Validation shipments to Return Confirm, and finally mark all processed delivery notes as verified.

2. The 5 Gates a Delivery Note Must Pass to Be Processed
Gate 1 — Feature flag ON
global_settings where type = 'delivery_note_auto_verification' must exist and setting_value = 1.
If the row is missing or value is 0 → the entire cron exits without processing anything.
Gate 2 — Schedule configured
global_settings where type = 'delivery_note_auto_verification_time' must exist.
If missing → the cron command is never registered with the Laravel scheduler at all (Kernel.php line 593–598).
Gate 3 — Hub not excluded
global_settings where type = 'delivery_note_auto_verification_exclude_hubs': any hub ID in the comma-separated list is skipped completely.
Delivery notes from excluded hubs never get auto-verified.
Gate 4 — Created within last 9 days
DeliveryNote::whereDate('created_at', '>=', Carbon::today()->subDays(9))
Notes older than 9 days are permanently ignored. If a note was stuck for 10+ days, it will never be auto-verified.
Gate 5 — Status = 0 AND pending_status = 1
status = 0 means not yet verified.
pending_status = 1 means the rider has submitted the note for verification.
Notes where the rider never pressed "Submit" (pending_status = 0) are never picked up, no matter how old they are.
3. Step-by-Step Processing Flow
1
Collect all matching delivery note IDs (pass Gates 1–5 above)
2
Get all delivery_note_shipments.shipment_id for those notes → DISTINCT list so a shipment in two notes is only processed once
3
Chunk shipments in groups of 1,000 for memory safety
4
For each chunk, load shipments excluding:
  • shipper_status_id IN (30, 36, 37, 56) — RP-EC, TB-DE, TB-PD, special types already finalised
  • booking_type_id = 6 — excluded booking type
5
Re-stamp journey: Call ShipmentsJourneyController::add() with the shipment's latest journey — essentially creating a new identical journey entry with verified_by = 346. This is what "verifying" the delivery means technically.
6
Trigger payment if shipper_status_id == 14 (Delivered):
  • booking_type_id = 1 → AdminFinanceController::add_payment($shipment->id, 0)
  • booking_type_id = 4 → AdminFinanceController::done_payment($shipment->id, 0)
7
Handle Reason Validation (status 12): If reason is Damaged (27) or Delivery Stopped (35) and journey count > 2 → auto-escalate to Return Confirm (status 20) and trigger return payment
8
Mark ALL collected delivery notes verified in one bulk UPDATE — regardless of whether individual shipments succeeded or threw exceptions inside the loop
4. When Payment Is Actually Added
booking_type_id = 1 (Normal / Standard Shipment)
if ($shipment->shipper_status_id == 14) {
    if ($shipment->booking_type_id == 1) {
        if (
            ($shipment->packaging_material_request == 1 && $shipment->packaging_material_charges != '')
            || $shipment->packaging_material_request == 0
        ) {
            AdminFinanceController::add_payment($shipment->id, 0); // ← payment added here
        }
        // If packaging_material_request=1 AND charges=NULL → payment is SILENTLY SKIPPED
    }
}

Inside add_payment(), there is one more guard:
CorporateUserOnDeliveredInvoice — if the shipper is on this list and the type is return (1) or adjustment (3), payment is skipped with a silent return.

booking_type_id = 4 (Walk-in)
if ($shipment->booking_type_id == 4) {
    AdminFinanceController::done_payment($shipment->id, 0);
}

// Inside done_payment():
if (DonePaymentShipment::where('shipment_id', $shipment_id)->where('type', $type)->exists()) {
    // creates new DonePayment ONLY if a DonePaymentShipment already exists
    // For a fresh walk-in delivery → no prior record → payment is NEVER created
}
Other booking types (2, 3, 5, etc.): No payment is triggered at all for these booking types — the cron only handles 1 and 4. If your operation uses other types, those shipments will never get payment from this cron.
5. Bug Catalog — Every Way a Shipment Can Get Stuck
BUG 1 Delivery note never submitted (pending_status = 0)
Cause: Rider creates the note but never taps "Submit for Verification" in the app. pending_status stays 0.
Effect: Gate 5 fails. Note is never picked up by the cron, ever.
Scope: All shipments on that note are stuck in their current status. Payment never drops.
Detection: SELECT * FROM delivery_notes WHERE status=0 AND pending_status=0 AND created_at < NOW()-INTERVAL 2 DAY;
BUG 2 Delivery note older than 9 days
Cause: Note was stuck (wrong hub, feature flag off, excluded hub) for more than 9 days. Cron's date window is Carbon::today()->subDays(9).
Effect: Gate 4 fails. Note is permanently outside the cron's window. It will never be auto-verified.
Detection: SELECT * FROM delivery_notes WHERE status=0 AND pending_status=1 AND created_at < NOW()-INTERVAL 9 DAY;
BUG 3 Hub is in the excluded list
Cause: Hub ID added to global_settings (type = 'delivery_note_auto_verification_exclude_hubs') for operational or cash-collection reasons and never removed.
Effect: Every delivery note from that hub skips auto-verification permanently until the hub is removed from the list.
Detection: Cross-check hub IDs in the excluded setting against hubs with stuck notes.
BUG 4 Packaging material charges missing (silent payment block)
Cause: Shipment has packaging_material_request = 1 but packaging_material_charges is NULL or empty string.
Effect: The condition ($packaging_material_request == 1 && $packaging_material_charges != '') is FALSE. Payment is silently skipped. No error, no log.
Scope: Shipment is marked delivered, delivery note gets verified, but payment is never added to pending_payments.
Detection:
SELECT id, tracking_number, shipper_status_id, packaging_material_request, packaging_material_charges FROM shipments WHERE shipper_status_id=14 AND packaging_material_request=1 AND (packaging_material_charges IS NULL OR packaging_material_charges='') AND payment_status_id NOT IN (1,5);
BUG 5 latest_shipment_journey is NULL → fatal exception → entire batch skipped
Cause: A shipment in the delivery note has zero rows in shipments_journey (data integrity gap).
Effect: $journey->shipment_id on line 103 throws Call to member function on null. The outer try/catch on line 58 catches it. The cron logs the error and exits. All remaining shipments in that chunk are skipped. But line 173 bulk-marks ALL delivery notes as verified anyway.
Result: Shipments after the bad one in the chunk are silently skipped but their notes are still marked verified — permanent payment loss with no easy recovery.
Detection:
SELECT dns.shipment_id FROM delivery_note_shipments dns LEFT JOIN shipments_journey sj ON sj.shipment_id = dns.shipment_id WHERE sj.id IS NULL GROUP BY dns.shipment_id;
BUG 6 Exception inside shipment loop marks ALL notes verified anyway
Cause: Any unhandled exception in the per-shipment processing (NULL journey, failed DB write, missing relation) propagates to the outer try/catch on line 58.
Effect: Line 173 DeliveryNote::whereIn(...)->update(['status' => 1]) is inside the if($delivery_notes->exists()) block, which runs before the exception is thrown during the loop. So all notes get verified even though only some shipments were processed.
Important: Actually looking at the code structure — line 173 is AFTER the foreach loop but INSIDE the same if block. If an exception escapes the foreach, line 173 is never reached. But the notes are NOT rolled back to status=0 either. On the next cron run, status=0 AND pending_status=1 still matches so they are re-processed — but only if they are still within the 9-day window.
BUG 7 Walk-in (booking_type_id=4) payment never created for new shipments
Cause: done_payment() only creates a payment if DonePaymentShipment::where('shipment_id', $id)->where('type', 0)->exists() is TRUE. For a first-time walk-in delivery, no prior record exists.
Effect: Every walk-in delivered shipment processed by this cron gets its journey re-stamped but zero payment is created.
Note: Walk-in payments may be intended to be created by a separate manual process, but the cron calling done_payment() on them gives the impression it should work.
BUG 8 Shipment is already in pending_payments — add_payment called again
Cause: A shipment's status was updated to 14 earlier (manual verification or another cron), add_payment was already called, and the shipment is now also in a delivery note that the auto-verify cron picks up.
Effect: add_payment runs again. Depending on its internal duplicate-check logic, this may create a duplicate pending_payment_shipments row — causing the shipment to be counted twice in payment.
Detection:
SELECT shipment_id, COUNT(*) FROM pending_payment_shipments GROUP BY shipment_id HAVING COUNT(*) > 1;
BUG 9 No transaction wrapping — partial success leaves inconsistent state
Cause: The entire cron runs outside a database transaction.
Effect: If a DB write fails midway (e.g., journey inserted but payment insert fails), the journey is stamped but payment is not. There is no rollback. The delivery note gets marked verified. The shipment is permanently stuck without payment.
Recommendation: Wrap each shipment's processing in a DB::transaction() with a per-shipment try/catch so a failure on one does not affect others and does not mark the note verified.
BUG 10 Feature flag missing → cron silently does nothing
Cause: If global_settings row for delivery_note_auto_verification does not exist, the outer if($setting->exists()) is false and the cron exits with no output, no log, no error.
Effect: Zero delivery notes are ever processed. All shipments silently accumulate without payment.
Verification:
SELECT * FROM global_settings WHERE type IN ('delivery_note_auto_verification','delivery_note_auto_verification_time','delivery_note_auto_verification_exclude_hubs');
6. Double Delivery Note — Duplicate & Stuck Shipment Problem

A shipment can be added to more than one delivery note at the same time because there is no UNIQUE constraint on delivery_note_shipments.shipment_id. This creates several problems:

Scenario A — Shipment in two OPEN notes, both submitted
The cron collects shipment IDs with DISTINCT, so the shipment is only processed once (correct). But BOTH delivery notes are marked verified at the end. If the first note was for Hub A and the second for Hub B, both hubs show the shipment as verified — confusing operational records.
Scenario B — Shipment in one VERIFIED note + one NEW note
The shipment already got its payment from the first note. When the second note is picked up, add_payment is called again.
If add_payment has no duplicate guard → duplicate pending_payment_shipments row → double payment.
If add_payment has a duplicate guard → the second call is silently ignored, but the second note is still marked verified. Operational records show a note was verified for a shipment that was already processed.
Scenario C — New note created while old note is still OPEN
Most common field scenario: rider returns without delivering, supervisor creates a new note for the next day. The old note is still open (status=0, pending_status=1). Both notes are picked up by the cron. The shipment is processed once (DISTINCT). The old note gets verified even though the actual delivery happened under the new note. Delivery records are attributed to the wrong date/rider.
Root cause of double notes: No validation at delivery note creation to check if a shipment already belongs to an open (status=0) note. The creation flow allows the same shipment to be added to multiple notes without warning.
Detection query for double delivery notes:
SELECT dns.shipment_id, COUNT(DISTINCT dns.delivery_note_id) AS note_count,
       GROUP_CONCAT(dn.id) AS note_ids,
       GROUP_CONCAT(dn.status) AS statuses
FROM delivery_note_shipments dns
JOIN delivery_notes dn ON dn.id = dns.delivery_note_id
GROUP BY dns.shipment_id
HAVING note_count > 1
ORDER BY note_count DESC
LIMIT 100;
7. Diagnostic SQL — Find Stuck Shipments
7.1 Delivered but not in pending_payments
SELECT s.id, s.tracking_number, s.user_id, s.shipper_status_id,
       s.booking_type_id, s.packaging_material_request, s.packaging_material_charges,
       s.payment_status_id, s.created_at
FROM shipments s
WHERE s.shipper_status_id = 14              -- Delivered
  AND s.booking_type_id = 1                -- Normal
  AND s.payment_status_id NOT IN (1, 5)    -- Not in pending or done payment
  AND s.shipment_type = 1                  -- Standard shipment
  AND NOT EXISTS (
    SELECT 1 FROM pending_payment_shipments pps
    WHERE pps.shipment_id = s.id
  )
ORDER BY s.created_at DESC
LIMIT 200;
7.2 Delivery notes never submitted by rider
SELECT dn.id, dn.hub_id, dn.rider_id, dn.created_at,
       COUNT(dns.id) AS shipment_count
FROM delivery_notes dn
LEFT JOIN delivery_note_shipments dns ON dns.delivery_note_id = dn.id
WHERE dn.status = 0
  AND dn.pending_status = 0
  AND dn.created_at < NOW() - INTERVAL 2 DAY
GROUP BY dn.id
ORDER BY dn.created_at ASC;
7.3 Open notes older than 9 days (cron blind spot)
SELECT dn.id, dn.hub_id, dn.rider_id, dn.pending_status, dn.created_at,
       COUNT(dns.id) AS shipment_count
FROM delivery_notes dn
LEFT JOIN delivery_note_shipments dns ON dns.delivery_note_id = dn.id
WHERE dn.status = 0
  AND dn.created_at < NOW() - INTERVAL 9 DAY
GROUP BY dn.id
ORDER BY dn.created_at ASC;
7.4 Shipments with packaging charges missing (payment silently blocked)
SELECT s.id, s.tracking_number, s.user_id,
       s.packaging_material_request, s.packaging_material_charges, s.payment_status_id
FROM shipments s
WHERE s.shipper_status_id = 14
  AND s.packaging_material_request = 1
  AND (s.packaging_material_charges IS NULL OR s.packaging_material_charges = '')
  AND s.payment_status_id NOT IN (1, 5);
7.5 Verify global_settings are all configured
SELECT type, setting_value, text
FROM global_settings
WHERE type IN (
  'delivery_note_auto_verification',
  'delivery_note_auto_verification_time',
  'delivery_note_auto_verification_exclude_hubs'
);
7.6 Shipments with no journey records (Bug 5 — crash trigger)
SELECT dns.shipment_id
FROM delivery_note_shipments dns
LEFT JOIN shipments_journey sj ON sj.shipment_id = dns.shipment_id
WHERE sj.id IS NULL
GROUP BY dns.shipment_id;
7.7 Duplicate pending_payment_shipments (double payment risk)
SELECT shipment_id, COUNT(*) AS cnt
FROM pending_payment_shipments
GROUP BY shipment_id
HAVING cnt > 1
ORDER BY cnt DESC;
8. Recommended Fixes Summary
Bug Severity Fix
BUG 5 — NULL latest_shipment_journey crashes batch Critical Wrap each shipment in try/catch inside the foreach. Log and skip bad shipments without crashing the batch.
BUG 9 — No transaction → partial success Critical Wrap each shipment's journey + payment in DB::transaction() per shipment.
BUG 6 — Notes marked verified even on crash Critical Move the bulk DeliveryNote::update(['status'=>1]) to after all per-shipment processing. Track which notes had errors and exclude them from the verified update.
BUG 4 — Packaging charges missing silently blocks payment High Log a warning when this condition is skipped. Add an operational alert for shipments with packaging_material_request=1 and no charges.
BUG 7 — Walk-in payment never created High Review the done_payment() gate logic. For walk-in deliveries via this cron, the guard should check if payment does NOT already exist (not if it does).
BUG 1 — Rider never submits note Medium Daily alert to hub managers listing notes older than 24h with pending_status=0.
BUG 2 — Notes older than 9 days Medium Extend the window to 14–21 days, or build a separate recovery tool for aged notes.
Double delivery notes Medium Add validation at note creation: prevent a shipment already on an open note from being added to a new note. Alert the creator.
BUG 8 — Duplicate pending_payment_shipments Medium Add UNIQUE constraint on pending_payment_shipments(shipment_id, type) or add explicit exists-check in add_payment before insert.
BUG 10 — Feature flag missing Low Add a startup health check that logs CRITICAL if the three required global_settings rows are missing.
BUG 3 — Hub excluded indefinitely Low Audit excluded hubs list quarterly. Add a UI note showing when each hub was added to the exclusion list.
Quick win: Run diagnostic queries 7.1 and 7.4 on production right now. Any shipments returned are already stuck and need manual add_payment() calls or a one-off recovery script.
