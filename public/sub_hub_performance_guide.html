Sub-Hub Wise Performance Report — Business Guide

This document explains how the Sub-Hub Performance Report works, how shipments are classified into categories, and — most importantly — why some shipments appear under a "Blank" sub-hub instead of a named one. It is intended for operations, finance, and management teams who use the report but do not need to read code.

Pilot Mode — Karachi & Lahore Only.  This report is currently active for Karachi and Lahore hub cities only (Hub IDs 202 and 223). All other cities are excluded from the report until the pilot is approved for nationwide rollout.

How Shipments Enter the Report (the "Universe")

Not every shipment booked through the system appears in this report. A shipment qualifies if it received one of these two journey events within the selected date range:

  • Status 2 — Arrived at Origin (S-AOC) — shipment has been scanned into the hub
  • Status 53 — Rider Picked (S-RP) — a rider has picked up the shipment for delivery

These two events mark the moment a shipment enters the hub's operational zone. The date filter on the report applies to when these events occurred, not when the shipment was booked.

Why conditional joins matter: The scanning journeys table stores the scanner's ID in a single column regardless of whether the scanner is an admin or a rider. If we join both admins and riders without restriction, an admin with ID 5 would accidentally match a rider with ID 5. The system prevents this by joining admins only when user_type = 1 and riders only when user_type = 5.
Excluded scan screens: Scans recorded on screen_location_id 9 (Tracking) and screen_location_id 18 (Retail Tracking) are view-only and are never used as sub-hub evidence. Only real operational scans count.

Why Shipments Show as "Blank" — The 5 Root Causes

A "Blank" row at a hub means the system could not identify which sub-hub those shipments belong to. Below are the five most common reasons, ordered by frequency:

1. OFD & Post-OFD statuses (5, 8, 12) — rider has no area assigned
When a rider picks a shipment and updates the status to Out for Delivery (5), Delivery Unsuccessful (8), or Confirmation Pending (12), the scan is made through the rider's mobile app. If that rider's profile in the system does not have an area_id, all five lookup levels fail and the shipment falls to Blank.
This is the most common cause of Blank — fix: ensure all active riders have an area (sub-hub) assigned in their rider profile.
2. Area log not written at scan time
The shipment_scanning_journey_area_logs table should receive a row for every scan. If the log row is missing (system error, network issue, or the admin performing the scan had no area at that moment), Level 1 of the lookup fails immediately. Levels 2–5 then provide the fallback.
3. Admin scanner has no area assigned
When an admin performs the last meaningful scan but their account has no area_id set, Levels 1 and 2 both fail. If there is also no rider link and no delivery note rider, the shipment ends up Blank.
4. View-only scan is the only scan on record
If the only scans recorded for a shipment were from screen 9 (Tracking) or screen 18 (Retail Tracking), the system finds no valid operational scan at all. All lookups return nothing → Blank.
5. No scan recorded at all
For shipments that were booked but never scanned (e.g. handed off outside the system, or data missing), there is no row in any scan table → Blank.
The modal drill-down will show "No scan recorded" next to these tracking numbers.

Percentage Calculations & Colour Coding

Two percentages are calculated for every row — sub-hub, hub, zone, and region:

Delivery %
Delivered ÷ Total × 100

Total includes all 5 categories plus excluded statuses (Booked, Cancelled).

≥ 80% — Green
60% – 79% — Orange
< 60% — Red
Return %
Returned ÷ Total × 100

A lower return rate is better — green means the sub-hub is performing well.

≤ 10% — Green
≤ 20% — Orange
> 20% — Red
Why do Delivery % + Return % not add up to 100%? Because there are three other categories (Delivery Pending, Return Pending, Lost/Closed) that each take a slice of the total. The percentages show the share of two specific outcomes, not a binary split.

Operational FAQ

Q: A large number of OFD shipments show under Blank — what is the immediate fix?

Go to the rider's profile in the admin panel and assign the correct sub-hub (area) to their account. As soon as the rider is updated, new scans will resolve correctly. Historical scans (before the fix) will not change — they remain Blank.

Q: Why does the same tracking number appear in multiple categories when I drill down?

A shipment can only be in one category (its current status), but if you are looking at the hub total drill-down, you see all shipments at that hub regardless of category. A shipment will appear once in the hub total but under one specific category column.

Q: The hub total doesn't match the sum of sub-hub rows. Why?

The hub total includes Excluded status shipments (Booked = 1, Cancelled = 17) which are added to the total but do not appear in any sub-hub row — not even Blank. This is by design: Booked/Cancelled shipments have no operational sub-hub relevance.

Q: Why are some statuses (e.g. status 44 — Return Rider Exchange) in two categories?

Status 44 can appear in either Return Pending or Lost/Closed. Return Pending requires that status 25 was previously logged; if it was not, and the current status is 44, it falls to Lost/Closed. The system checks these conditions sequentially.

Q: The report loads slowly for wide date ranges. Is that expected?

Yes. The system first fetches all qualifying shipment IDs from the journey table, then enriches each with its hub/zone/region, and then runs 5 separate sub-hub attribution queries. For a pilot with only 2 cities this is manageable. If the pilot expands to all hubs, performance optimisation will be needed.

Q: Can the report be used for cities other than Karachi and Lahore?

Not currently. The pilot restriction is controlled by a constant in the system (PILOT_HUB_IDS = [202, 223]). Expanding to all hubs requires changing this constant after the pilot is approved.

Diagnostic SQL — Find Riders Without Area Assigned

Run this query against the production database to identify which riders are causing the most Blank shipments due to missing area assignment:

-- Riders who have scanned shipments in OFD/Attempt statuses
-- but have no area_id set (causing Blank sub-hub)
SELECT
    r.id             AS rider_id,
    r.name           AS rider_name,
    r.area_id,
    COUNT(DISTINCT ssj.shipment_id) AS affected_shipments
FROM shipment_scanning_journeys ssj
INNER JOIN riders r ON r.id = ssj.admin_id AND ssj.user_type = 5
INNER JOIN shipments s ON s.id = ssj.shipment_id
WHERE r.area_id IS NULL
  AND s.shipper_status_id IN (5, 8, 12)   -- OFD, Unsuccessful, Reason Required
  AND ssj.created_at >= DATE_SUB(NOW(), INTERVAL 7 DAY)
GROUP BY r.id, r.name, r.area_id
ORDER BY affected_shipments DESC
LIMIT 50;

-- Quick count: how many shipments are Blank due to rider missing area
-- in the last 7 days (OFD + post-OFD statuses only)
SELECT COUNT(DISTINCT s.id) AS blank_due_to_rider_no_area
FROM shipments s
INNER JOIN shipment_scanning_journeys ssj ON ssj.shipment_id = s.id
LEFT  JOIN shipment_scanning_journey_area_logs al ON al.shipment_scanning_journey_id = ssj.id
INNER JOIN riders r ON r.id = ssj.admin_id AND ssj.user_type = 5
WHERE s.shipper_status_id IN (5, 8, 12)
  AND al.area_id IS NULL
  AND r.area_id IS NULL
  AND ssj.created_at >= DATE_SUB(NOW(), INTERVAL 7 DAY);
