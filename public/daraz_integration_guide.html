Daraz Booking API — Technical Reference

Complete reference for the Daraz-specific shipment booking endpoint: request format, parameters, example payloads, and a full technical comparison with the standard Sonic booking API.

POST /api/shipment/book/daraz Auth: APIToken middleware Accounts: 7306 · 7308 · 10389 Service Type: Standard (1) only Shipping Modes: Rush (1) · Saver (2)
1 API Request Format

Endpoint

POSThttps://<domain>/api/shipment/book/daraz // Route: routes/api.php → middleware('APIToken') → APIController@shipment_book_daraz

Authentication & Headers

Important: The Authorization header holds a raw API token (no Bearer prefix). The middleware looks up the user from users.api_token and injects user_id into the request automatically. Do not send user_id in the request body.
HeaderRequiredValueNotes
Authorization Required Raw API token string Matched against users.api_token. Account must be active (status=3), not blacklisted, phone verified. No "Bearer" prefix.
Content-Type Required application/json Body must be JSON.
Via Optional 1 for Trax App Used internally to detect app_type. Omit for direct API calls.

4 What Needs to Be Added to the Daraz API

These features exist in the current normal API but are absent from the Daraz API. Priority order: highest risk first.

1.Negative payable balance check. Add PendingPayment::check_negative_payable() + NegativePayableAllowShipperZeroCod::isAllowed() at the top of the method. Currently Daraz accounts can book unlimited zero-COD shipments even when the account is frozen for non-payment.
2.Blacklisted consignee check. After booking, look up phone in ConsigneeInformation → BlacklistedConsignee. Return a blacklisted_consignee warning. Currently known bad consignees can book via Daraz without any flag.
3.booking_enable_status city check. Add if (!$consignee_city->booking_enable_status) check. Daraz can currently book to cities where system-wide booking is disabled.
4.BookingApiLog creation. Add BookingApiLog::create(['user_id'=>$user_id, 'shipment_id'=>$shipment_id, 'endpoint'=>'book_daraz', 'ip'=>$request->ip(), 'payload'=>$request->all()]) after booking. Currently no audit trail exists for Daraz bookings.
5.PaymentModeLog creation. Add PaymentModeLog::create([...]) after booking for finance reconciliation.
6.addressAreaConsigneeShipper() call. Add ShipperShipmentBookController::addressAreaConsigneeShipper($shipment_id, $pickup_address_id, $consignee_city_id, $consignee_address) after booking. This sets address area mapping used by routing and sub-hub reporting.
7.NSA keyword check. Scan consignee address against NonServiceArea table and return a non_service_area warning in the response when matched.
8.parcel_value support. Accept parcel_value in validation rules and pass it to corporate_book(). When amount=0, require parcel_value > 0 (unless account is in bypass list).
9.Updated phone regex. Replace the old static regex with the dynamic dual-regex used by the normal API (strict for 92/03 prefix, loose for others).
10.order_id uniqueness. Add Rule::unique('shipments','order_id')->where(fn($q)=>$q->where('user_id',$user_id)) to the order_id rule. Prevents silent duplicate order submissions.
11.Validation error logging. Add Log::error('Daraz Booking API', ['user_id'=>$user_id, 'errors'=>$validate->errors()]) on validation failure for observability.
12.Multi-prefix tracking number support. The current prefix check reads only the first ShipmentPrebook row. Replace with a loop over all prebook prefixes (same pattern as the normal API) to support multiple Daraz account prefixes.
5 What is Unique to Daraz (Intentional Design)

These are deliberate design choices for the Daraz integration. Do not remove them.

→Caller-provided tracking number. Daraz sends their own TN format. The system books internally, then overwrites with $shipment->tracking_number = $tracking_number; $shipment->save(). This keeps Daraz's TN visible end-to-end. Normal API never accepts an external TN.
→Return address auto-creation by vendor+city. Instead of requiring a pre-registered address ID, Daraz passes raw return fields per shipment. System looks up (user_id, vendor, city_id) — creates a new user_shipping_infos record if not found. This avoids requiring Daraz to pre-register addresses before booking.
→Hardcoded product type 24. All Daraz items use a fixed product category. Agreed with Daraz — not configurable per shipment.
→Standard delivery only (service_type = 1). Daraz does not use Replacement, Try & Buy, Pickup, or FTL. Locking prevents accidental misuse.
→Account whitelist gate. [7306, 7308, 10389] are the only Daraz Sonic accounts. The hardcoded gate prevents any other shipper from using this endpoint even if they have a valid API token.
→Shipping mode limited to 1–2. Same-Day (4) and other modes not offered to Daraz as per commercial agreement.
6 Stale / Old Code in the Daraz API
Old phone number regex. The validator uses a legacy pattern that accepts formats like 300-1234567 (no leading zero) and bare 10-digit numbers. The normal API was updated to a stricter dual-regex and the Daraz one was never synced. Should be updated to match.
Dead self_collection code. The method includes logic to handle self_collection from the request, but this field is not in the validation rules and Daraz never sends it. Copied from the original API and has no effect.
$shipment_pre_book = null dead assignment. After the prefix check block, $shipment_pre_book = null is set. This does nothing — leftover from an earlier refactor.
Unreachable service_type_id == 5 branch. The origin_check validator has if ($service_type_id == 5) return true. Since $service_type_id is hardcoded to 1 in that closure, this branch can never be reached.
Commented-out document status block. Both APIs share the same commented-out block checking document_status IN [0,3]. Was live until 2026-03-31. Dead code in both.
7 Tracking Number Flow — Daraz vs Normal
DARAZ FLOW
1
Daraz sends tracking_number = their own TN (e.g. MYP0012345678).
2
Validated: unique in shipments, first N chars = ShipmentPrebook.prefix.
3
corporate_book() called — system generates an internal Sonic TN temporarily.
4
TN override: $shipment->tracking_number = $tracking_number; $shipment->save() — Sonic TN replaced with Daraz TN.
5
Response echoes the Daraz TN back to the caller.
Risk: If $shipment->save() fails after booking, the shipment exists with the Sonic TN but the caller gets an error. The Daraz TN is never saved. No rollback or retry logic exists.
NORMAL FLOW
1
book() or corporate_book() creates the shipment.
2
If prebook exists: generate_prefix_tracking_number($shipment_id, $order_id) → prefix + numeric portion.
3
If no prebook: generate_tracking_number($shipment_id, $pickup_city_id, $consignee_city_id) → standard Sonic format.
4
TN returned in response. Caller has no control over TN.
8 Return Address Auto-Creation Logic
1
Caller sends: return_vendor, return_city_id, return_address, return_contact_person, return_phone_number, return_email_address.
2
Lookup: UserShippingInfo::where('user_id',$user_id)->where('vendor',$return_vendor)->where('city_id',$return_city_id)
3
If found: Use existing record ID as return_address_id. The address/contact/phone/email from the request are silently ignored — the existing record is NOT updated.
4
If not found: ShipperShipmentBookController::add_pickup_address(...) creates a new record. New ID used as return_address_id.
5
Return city validated for serviceability via check_return_destination($return_address_id, $shipping_mode_id, $user_id).
Known issue — stale data: If Daraz changes their warehouse address or contact details, the new values in the request are silently ignored because the old (vendor, city_id) record already exists. The old details remain on file until manually updated in the admin panel.
Known issue — silent creation failure: If add_pickup_address() returns null, $return_address_id becomes null and the booking proceeds with an invalid return address ID. No error is thrown.
9 Daraz Booking — Complete Execution Flow
1
Account gate — reject if user_id (from token) not in [7306, 7308, 10389].
2
Validation — tracking_number (required, unique, prefix check deferred), pickup_address_id, all 6 return fields, consignee fields, shipping_mode_id (1–2), estimated_weight, amount, item_description, item_quantity, reference fields.
3
Prefix check — first N chars of tracking_number must equal ShipmentPrebook.prefix for this account.
4
Return address resolve — lookup user_shipping_infos by (user_id, vendor, city_id). Create new record if not found.
5
Return city serviceability — check_return_destination($return_address_id, $shipping_mode_id, $user_id).
6
Pickup address checks — status active, city status active, city has zone, pickup enabled for that city.
7
Return address checks — status active, city status active, city has zone.
8
Consignee city checks — status active, city has zone.
9
Same-day mode check — if shipping_mode_id=4 and pickup city ≠ consignee city, reject. (Mode 4 is actually blocked at validation, so this is a redundant safety check.)
10
COD cap check — inter-city only: looks up zone class for consignee city, compares amount against global_settings cod_cap_for_zone_class_X.
11
City delivery check — city_deliveries table: consignee_city_id + service_type=1 + shipping_mode_id must have an active row.
12
Book shipment — corporate_book(service_type=1, payment_mode=1, charges_mode=3, delivery_type=1, pieces=1, open=0, return_address_id).
13
Override tracking number — $shipment->tracking_number = $tracking_number; $shipment->save().
14
Save order_date — if provided, insert into shipment_order_dates.
15
