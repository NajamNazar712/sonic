Bug Report — Return Note: Duplicate Shipment via Bag Quick Receive

A shipment assigned to an open return note gets reset to RT-AOC by a delayed bag scan submission, allowing a second return note to be created for the same shipment — leaving the first note permanently uncloseable.
Severity: High Reported: May 2026 Affected: Return Operations Status: Under Review
1 Incident Summary
Problem: A shipment that is already dispatched on an open return note (status = RT-DP) gets its status overwritten back to RT-AOC by the Quick Receive Bag screen submission. Because the status returns to RT-AOC, the same shipment can be added to a new return note. The original return note cannot close because the shipment's entry in it is still pending (status = 0).

Why Return Note 590296 Cannot Close

The close logic in ReturnController::return_note_update_status() counts unconfirmed shipments before closing:

// line 3834 — ReturnController.php
$shipment_status = ReturnNoteShipment::where(['return_note_id' => $return_note_id, 'status' => 0])->count();
if ($shipment_status == 0) {
    $return_note_details->status = 1; // close the return note
}

Shipment 57705486 is detected as belonging to a newer return note (591017 > 590296) at line 3811, so it is skipped — its entry in return_note_shipments for 590296 is never updated to status=1. The count remains 1, so the return note stays open.

3 Root Cause — Two Bugs Working Together

Bug 1 — Primary: Quick Receive Bag Does Not Check for Active Return Notes

File: app/Http/Controllers/Admins/AdminMasterCargoController.php
Method: master_cargo_bag_quick_receive_store()

When the admin submits the quick receive, the code processes each shipment in the submitted list and sets its status to 22 (RT-AOC). It checks that the bag shipment record exists and is pending, but it does not check the current status of the shipment or whether it is already dispatched on an active return note.

// Current code — no guard against active return notes
$shipment->shipper_status_id = $shipper_status_id; // always 22 for booking_type 1
$shipment->consignee_status_id = $consignee_status_id;
$shipment->save();
ShipmentsJourneyController::add($shipment_id, $shipper_status_id, $consignee_status_id, ...);

The gap: There is a 2-hour window between when admin 4511 scanned the shipment (16:28) and when they submitted (18:27). During that window, another admin had already dispatched the shipment on return note 590296. The submission did not check this.

The same issue exists in AdminCargoController::quick_receive_store() for cargo consignment quick receive.

Bug 2 — Secondary: Return Note Creation Guard Misses Status-0 Entries

File: app/Http/Controllers/Admins/ReturnController.php
Method: return_note_create() — line 3203

Before adding a shipment to a new return note, the code checks if the shipment is already in an open return note. But the query only looks for entries where return_note_shipments.status = 1 (confirmed/received):

// Current guard — MISSES status=0 entries
$old_return_note_id = ReturnNoteShipment::where('shipment_id', $shipment_id)
    ->where('status', '=', 1)  // ← ONLY looks for confirmed entries
    ->orderBy('return_note_id', 'desc');

if ($old_return_note_id->exists()) {
    // checks if that return note is still open...
}

The shipment's entry for return note 590296 has status = 0 (dispatched, not yet confirmed/received). The guard never detects it, so the system happily creates return note 591017 for the same shipment.

Guard ScenarioDetected?Why
Shipment confirmed in an old open return note (status=1) Yes Covered by where('status', 1)
Shipment dispatched but not yet confirmed in open return note (status=0) No status=0 is excluded from the query — this is the bug
4 Code Fix

Fix 1 — AdminMasterCargoController::master_cargo_bag_quick_receive_store()

Before overwriting the shipment status to 22, check if the shipment is currently dispatched on an open return note. If so, skip the status update.

// Add this check BEFORE setting $shipment->shipper_status_id = $shipper_status_id (for type != 1 bags)

$in_active_return_note = \App\Http\Models\Admin\ReturnNoteShipment::where('shipment_id', $shipment_id)
    ->where('status', 0)  // dispatched, not yet confirmed
    ->whereHas('return_note', function ($q) {
        $q->where('status', 0); // return note still open
    })
    ->exists();

if ($in_active_return_note) {
    // Shipment is already dispatched with a rider on an open return note.
    // Do not reset its status. Log and skip.
    \Illuminate\Support\Facades\Log::warning('Quick receive skipped for shipment already on active return note', [
        'shipment_id' => $shipment_id,
        'admin_id'    => Auth::id(),
    ]);
    continue;
}

// ... existing status assignment code below ...
Apply the same fix to: AdminCargoController::quick_receive_store() — the same timing gap vulnerability exists there for cargo consignment receives.

Fix 2 — ReturnController::return_note_create() — Secondary Guard

Extend the existing guard to also block shipments that are already in open return notes at status=0 (dispatched but not yet confirmed).

// BEFORE (line 3203) — misses status=0 entries:
$old_return_note_id = ReturnNoteShipment::where('shipment_id', $shipment_id)
    ->where('status', '=', 1)
    ->orderBy('return_note_id', 'desc');

// AFTER — check for ANY open return note (status=0 or status=1):
$already_in_open_rn = ReturnNoteShipment::where('shipment_id', $shipment_id)
    ->whereHas('return_note', function ($q) {
        $q->where('status', 0); // return note is still open
    })
    ->exists();

if ($already_in_open_rn) {
    // Skip this shipment — it is already in an open return note
    // Do not decrement $shipments_count; remove from valid_shipments
    $shipments_count--;
    continue;
}
Note on the ReturnNoteShipment model: Ensure the return_note() relationship is defined on ReturnNoteShipment before using whereHas. It is already defined at line 34 of app/Http/Models/Admin/ReturnNote.php (inverse direction). Verify ReturnNoteShipment::return_note() exists or add: public function return_note() { return $this->belongsTo(ReturnNote::class); }
5 Immediate Manual Fix for Return Note 590296
Important: These SQL statements modify production data. Run only after confirming the current state matches the values shown. Run ONLY SELECT queries first to verify, then run the fix.

Step 1 — Verify Current State (SELECT only)

-- Confirm the stuck entry
SELECT return_note_id, shipment_id, status, update_type
FROM return_note_shipments
WHERE return_note_id = 590296 AND shipment_id = 57705486;
-- Expected: 1 row, status = 0

-- Confirm return note is still open
SELECT id, shipments_count, status FROM return_notes WHERE id = 590296;
-- Expected: status = 0, shipments_count = 19

-- Confirm the shipment has been resolved elsewhere
SELECT id, shipper_status_id FROM shipments WHERE id = 57705486;
-- Expected: shipper_status_id = 25 (RT-DS — already returned to shipper via RN 591017)

Step 2 — Remove the Stuck Entry

-- Remove the orphaned return note shipment entry
DELETE FROM return_note_shipments
WHERE return_note_id = 590296
  AND shipment_id = 57705486;

Step 3 — Correct the Shipments Count

-- Decrement shipments_count by 1 (was 19, should be 18)
UPDATE return_notes
SET shipments_count = 18
WHERE id = 590296;

Step 4 — Verify the Fix

-- Confirm no more status=0 entries remain for return note 590296
SELECT status, COUNT(*) AS cnt
FROM return_note_shipments
WHERE return_note_id = 590296
GROUP BY status;
-- Expected: only status=1 rows (18 of them)

-- Return note should now be closeable by the rider
SELECT id, shipments_count, status FROM return_notes WHERE id = 590296;
-- shipments_count = 18, status = 0 (admin still needs to process close it)
After the manual fix, the rider/admin can go to return note 590296 and process the remaining 18 shipments normally. The note will close when all 18 reach status=1 in return_note_shipments.
